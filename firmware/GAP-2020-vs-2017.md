# What the 2020 Accord kit mapped vs. what we have on the 2017 (T2F) — gap + flashing

**Date:** 2026-11-23. EVIDENCE unless marked. The 2017 is `39990-T2F-L310`
(µPD70F3413, V850E/PG2); the 2020 is `39990-TVA-A160` (µPD70F3508, V850E2).

## ⚠ CORRECTION (2026-11-23, later): the transport is K-LINE, not CAN

My first pass assumed the 2017 flashes over CAN like the 2020. **Decompilation shows
otherwise.** The 2017 EPS diagnostic + reprogramming runs over **UART channel U1 using
Honda's proprietary serial (K-line-class) protocol**, not UDS-over-CAN:

- The diagnostic request buffer (`0x3FFD40D`) is filled **only** by the U1 serial RX
  handler `FUN_0001dc68` (length-prefixed: byte[1]=length, collect, respond) — nothing
  from a CAN handler writes it. CAN (`C0`) carries vehicle signals only. EVIDENCE.
- The dispatcher `FUN_0001da3c` branches on request byte[0] with **Honda-proprietary
  command IDs `0xC0 0xC1 0xC2 0xC3 0xC4 0xC5 0xC7 0x7D 0xFE`** — NOT the UDS
  `0x10/0x27/0x34`. Response checksum = `~sum+1` (`FUN_0001ecec`).
- **SecurityAccess = command `0xC2`** (`FUN_0001d71c`): a sub-dispatcher with a seed/key
  handshake gated by request flags (`cRam03ffd7ec/7f1`), granting unlock via
  `FUN_0001d36c` (`bRam03ffd438 |= 8`). Commands `0xC0`/`0xC7` are gated behind that
  unlock = the protected reprogramming path; subcmds `0x08`→`FUN_00010614` and
  `0x03`→`FUN_0001a160` (address bounds `0x4000`/`0x8000`) are the memory read/program ops.
- The seed→key **crypto itself is a deeper multi-function Honda scheme**
  (`FUN_0002ede4`/`0002eea0`/`000170fc`/`00016f80` …), **NOT** the 2020's
  `(seed+k0)^((seed*k1)%k2)` — not yet fully extracted. (The 2020 Group-C constants are
  absent from this image, consistent with a different scheme.)

**Consequence:** the kit's `eps-update-tva.py` (CAN/UDS) will **not** flash a T2F as-is —
its "T2F in scope" note was an assumption from the shared `.rwd` format, not the transport.
Flashing a T2F needs a tool speaking Honda's **K-line `0xCx` protocol** with the `0xC2`
seed/key unlock (what iHDS/MVCI does at a dealer). The `.rwd` payload/cipher we decoded is
still correct; only the delivery transport differs.

### Deeper result (2026-11-23): the reflash stack is BOOTLOADER-resident, not in this image

Tracing the `0xC2` SecurityAccess and the gated `0xC0`/`0xC7` commands shows the
application's `0xCx` protocol is **diagnostics only**: live-data read (`0xC0` →
`FUN_0001d928`, pointer table `0x8EFC`), readout sub-commands (`0xC7` → `FUN_0001ca48`),
actuator-test mode (`0xC2` `0xA3/0xA4` → `FUN_000170fc`/`00016f80`, override values
`0x3FFDCBA…`), ID read (`0xC5`), and **bounded RAM/EEPROM adjustment** writes (`0xC2`
`0x03/0x08` → `FUN_0001a160`/`00010614`, mailbox `FUN_00010648`→`0x3FFCD54`). **No
main-flash erase/write, and no seed→key crypto, is present.** The `0x438|8` "unlock" gates
diagnostic/adjustment commands, not reprogramming.

**Structural certainty:** code that erases+rewrites `0x1800–0x38000` cannot live in that
range; it lives in the protected boot sector `0x0–0x17FF` — a resident **bootloader** that
the `.rwd` does not contain. ⇒ **the reprogramming SecurityAccess (seed→key) AND the
flash-write sequence are in the bootloader, NOT in this `.rwd`-derived image.** Extracting
either needs a **chip dump of the boot block** (the `0x0–0x17FF` the `.rwd` omits).

Net: the dealer `.rwd` fully supports mapping the **control/torque** firmware (done), but
**not** the reflash/security stack. Flashing a T2F still goes over Honda **K-line** with its
bootloader's own security — reverse-engineering that requires the boot block.

### Reflash routes — full picture (2026-11-23)

**CAN reflash: NO (EVIDENCE).** No UDS-over-CAN diagnostic addressing exists in the image
(`0x18DA80F1`/`0x18DB33F1` = 0 hits), and the diagnostic request buffer is written only by
the U1 serial handler. CAN (`C0`) is used purely to receive vehicle signals — `FUN_0001a5e8`
decodes/scales speed → `0x3FFD648` (the value the PID schedules on). There is no CAN
diagnostic session, no CAN SecurityAccess, no CAN programming path.

**The ways to reflash this ECU:**

| route | where | needs | status |
|---|---|---|---|
| **Honda K-line** (dealer/iHDS) | in-vehicle or bench, via U1 serial | app→bootloader jump + **bootloader SecurityAccess** | bootloader + its crypto are in the boot block `0x0–0x17FF` — **not in this image**; RE needs a chip dump or a sniffed dealer reflash |
| **Renesas serial boot mode** (FLMD0) | **bench only**, chip's native boot ROM over UART | FLMD0+reset entry; a programmer / extended tool for erase+write; a **complete image incl. boot block** | ⭐ bypasses Honda's protocol entirely — the practical bench path; same entry as the firmware *dump* |
| **flashPRO / HW programmer** | bench | same boot interface | equivalent to the above with vendor tooling |
| **CAN UDS** | — | — | **not supported by this firmware** |

⭐ **Recommended bench path (matches the spare-EPS setup):** enter Renesas boot mode on the
spare unit → **dump** the full flash (this finally gives the missing boot block `0x0–0x17FF`
+ vectors) → modify the cal in the complete image → **write back** via boot mode. This needs
no Honda K-line security at all. ⚠ Risk: the chip may carry a Renesas flash **security
setting** (write/readout protection); check it in boot mode before relying on write. And the
boot-mode write programs the whole chip, so a complete, correct image is mandatory.

**Adjustment-write (`0xC2 03/08`) is NOT a reflash or a torque tuner (EVIDENCE):** it sets a
bit in a mailbox (`0x3FFCD54`) consumed by `FUN_00011ffc`, a 16-way dispatcher of **service/
NVM tasks** (bounded, gated). It performs service operations (sensor zero / variant coding
class), not free calibration writes — it cannot change the torque-ceiling cells.

The CAN-based section below is **superseded** by this correction; kept for the inventory.

## [SUPERSEDED] CAN THE 2017 BE FLASHED? — Yes, same mechanism as the 2020, with ONE gate

The 2020 is flashed by **UDS reprogramming over the diagnostic CAN bus** (not the LKAS
transport) with `flashing-2020accord/eps-update-tva.py`: tester-present → read app id →
extended session → **SecurityAccess (0x27)** → erase → transferData (0x34/0x36/0x37). The
`.rwd` payload is written to flash.

**The 2017 fits this path:**
- ✅ The flasher's scope **explicitly names "9th-gen Accord T2F/T3L"** as supported.
- ✅ `39990-T2F-L310.rwd` is an **x31 V850 container** (decoded — same format the flasher writes).
- ✅ Diagnostic **CAN ID = `0x18DA80F1`** (from the `.rwd` `%` header `80`, same as TVA).
- ✅ The EPS has a CAN controller (`C0`) — reachable for UDS over OBD/diagnostic CAN.

**The gate — SecurityAccess key (EVIDENCE it is NOT yet known for T2F):**
- The TVA key is `key = ((seed+0x0211)&0xFFFF) ^ ((seed*0x0212) % 0x1220)`, constants at
  TVA flash `0x92C0`.
- Those constants are **absent from the T2F image** (`0x92C0` holds unrelated bytes; the
  pattern `11 02 12 02 20 12` is nowhere in the file). The 2017 is a different V850
  sub-family + compile, so it has its **own SA constants** → net-new derivation.
- ⇒ Until the T2F SecurityAccess routine (the `0x27` handler) is found and its constants
  read, the flasher's SA handshake would fail on a T2F. **This is the single thing standing
  between us and flashing.** It is findable (the UDS `0x27` service handler in the image).

**Also required (standard, not blockers):** physical panda on the EPS diagnostic CAN; kill
pandad first; confirm file+bus; for a *modified* build, a correct x31 re-encode + `.rwd`
CRC (kit's `encode_eps.py` round-trips T2F byte-identically — BELIEF it extends to a
modified payload) **and** the dual cal-bank + cal-CRC handled (see `CALIBRATION` note).

> Note: flashing is over **CAN/UDS**, independent of the LKAS **serial** transport. So even
> though the camera link is UART, the firmware is reflashed the same way the 2020 is — which
> means a modified T2F image could be flashed without the serial board, once the SA key is known.

## Recommended order to close the gap

1. **SecurityAccess routine** (`0x27` handler) → derive the T2F SA key. *Unblocks flashing.*
2. **Motor driver stage** (`0x3FFEC2E` → motor) + **base assist** — completes the torque path.
3. **CAN RX map** — vehicle signals; also settles the dormant-`0xE4` question.
4. **Cal CRC / dual-bank verifier** — required before any modified flash.
5. Safety: lockstep, EME/governor, DTC thresholds — before trusting any mod on-car.
